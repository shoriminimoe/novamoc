# ADR-006: Use Hybrid Logical Clocks for Event Ordering

## Status

Accepted

## Context

When multiple clients generate events against a shared dataset and sync asynchronously, we need a way to order events so that all participants converge on the same projection. The ordering mechanism must work while clients are offline (no server coordination available at event generation time) and must be resilient to client clock skew.

Three candidate approaches:

**Wall-clock timestamps (`Date.now()`).** Human-meaningful and cheap, but unreliable for ordering. Clocks drift, laptops sleep, phones resync to NTP and jump backward, users change timezones. Two events milliseconds apart on different devices can appear in the wrong order.

**Lamport clocks.** A pure logical counter incremented on each event and advanced to `max(local, received) + 1` on receipt. Guarantees causal ordering but has no relationship to wall time, making it useless for UI concerns like "edited 5 minutes ago" or sorting by recency.

**Hybrid Logical Clocks (HLCs).** A tuple of (physical time, logical counter, node id) combining the strengths of both. The physical component tracks wall time closely enough to be human-meaningful. The logical counter breaks ties and preserves causal ordering when physical time hasn't advanced or has moved backward. The node id breaks ties across devices.

HLCs are the standard mechanism used by modern local-first sync systems (Evolu, ElectricSQL, cr-sqlite) precisely because they solve both problems at once.

## Decision

Every event carries a Hybrid Logical Clock timestamp generated by the originating client at event creation time.

**Structure.** An HLC is a tuple `(physical_ms, logical, node_id)`, serialized as a fixed-width zero-padded sortable string: `{physical_ms:016}-{logical:05}-{node_id}`. Stored as `TEXT` in SQLite. Lexicographic comparison yields the correct HLC ordering.

**Local event algorithm.** On generating a local event:
```
wall = Date.now()
if wall > hlc.physical:
    hlc.physical = wall
    hlc.logical = 0
else:
    hlc.logical += 1
```

**Receive event algorithm.** On receiving a remote HLC:
```
wall = Date.now()
new_physical = max(hlc.physical, remote.physical, wall)
if new_physical == hlc.physical == remote.physical:
    hlc.logical = max(hlc.logical, remote.logical) + 1
elif new_physical == hlc.physical:
    hlc.logical += 1
elif new_physical == remote.physical:
    hlc.logical = remote.logical + 1
else:
    hlc.logical = 0
hlc.physical = new_physical
```

**Clock drift protection.** The server rejects incoming events whose HLC physical component is more than a bounded drift ahead of the server's wall time (we propose 1 minute as a starting value). Because rejection happens at the server — the single point through which all events pass before fan-out — every client sees the same accepted set of events and the determinism guarantee in ADR-007 holds. Clients do not independently reject received events on drift grounds: they trust the server's decision, advancing their local HLC from received events as described in the receive-event algorithm above. This prevents a single client with a badly-wrong clock from poisoning the HLC state of every other participant while preserving a single source of truth for event acceptance.

**Node identifier.** Each client generates a stable `node_id` on first launch, persists it locally, and reuses it for all future events. The node id is opaque and not reused across devices.

## Consequences

Events order deterministically across all participants given the same event set. The projection fold (ADR-007) becomes a simple HLC comparison — the event with the largest HLC wins for its field.

HLC string comparison in SQL works as plain `TEXT` comparison, which means `ORDER BY hlc DESC` and `hlc > ?` work without custom collations. This materially simplifies the sync endpoint and the fold.

The physical component stays close enough to real time to be shown in the UI as a timestamp. We do not need a parallel wall-clock column for display purposes.

The drift bound is a trade-off: too tight and legitimate clock differences cause rejections; too loose and a bad clock can push HLCs far ahead. One minute is a reasonable starting point for small-team use and can be tuned.

Implementing HLCs ourselves is approximately 100 lines of code plus tests. This is acceptable given we are hand-rolling the sync engine (ADR-010) and gain full control over behavior.
